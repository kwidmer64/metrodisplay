# MetroDisplay — Design Session Summary (2026-09-22)

## What this project is

An always-on display rendering rail transit systems as minimal wireframe maps with live
vehicle positions from GTFS-RT feeds, rotating between cities every ~5 minutes. Art from
across the room, real data up close. v1 is a web page; endgame is a small dedicated screen
driven by a Pi or similar.

## Decisions made, with rationale

| Axis | Decision | Why |
|---|---|---|
| Map geometry | Simplified geographic (Douglas–Peucker), never octolinear | Octolinear is NP-hard and hand-drawn in practice; it also breaks lat/lon → screen identity, turning "add a city = config file" into "add a city = an afternoon of drawing" |
| Scale | Uniform — one meters-per-unit for the whole map | 2 km downtown and 2 km in the suburbs must be the same length on screen |
| Extent | Real-distance radius from a configured city core point | Makes scale statable: "Boston shows 44 km across". Percentile-of-points framing was rejected as density-weighted and unpredictable |
| Overflow | Hard clip at the edge + `TO <TERMINUS>` label | Clipping keeps scale honest; the label makes the cut read as deliberate |
| Off-map vehicles | Dropped from map, retained in counts, counts labelled system-wide | Counts stay true to service; the label stops the mismatch reading as a bug |
| Layout | Full-width map + dense bottom rail | Most metro bboxes are ~1:1 on a 1.78:1 screen, so a rail costs nothing real; a sidebar would eat needed width and require a second layout at 800×480 |
| Vehicle motion | Tween along the track polyline between polls | Dead reckoning needs `speed`/`bearing`, which are optional in GTFS-RT and often absent; it would silently degrade per-city |
| RT feeds | VehiclePositions + ServiceAlerts. No TripUpdates in v1 | Counts are free from positions; delays would need a second, much larger feed |
| Topology | Hosted backend, thin displays | One feed poll regardless of display count; API keys stay server-side |
| Scene contract | Normalized unit-space coords, server-side projection | One projection implementation ever; one scene serves a 1920×1080 browser and an 800×480 panel identically |
| Message split | `network` (per city switch) + `frame` (per poll) | Cadences are five orders of magnitude apart — combining them would resend ~200 KB every 20 s to deliver a few hundred bytes |
| Transport | Server-Sent Events, `POST /control` reserved | Nothing flows client→server; `EventSource` gives reconnect + `Last-Event-ID` for free, which matters for an unattended display. Originally specced as WebSocket and changed on challenge |
| Transition | Crossfade, ~700 ms | Hard cut is jarring in a dim room; zoom-out/zoom-in breaks when systems differ in extent |
| Backend | .NET 10 (`net10.0`) | SDK 10.0.401 confirmed installed |
| Renderer | TypeScript, canvas2d | Immediate-mode drawing matches what a future Pi framebuffer renderer implements — the port becomes a transcription, not a redesign |
| Static GTFS | Separate project building versioned artifacts, run in-process, daily conditional GET | 304 costs nothing; a separate microservice would add a deploy unit to serve one consumer |
| Cities | Start with 2–3 (MBTA, BART, WMATA expected), registry-driven | Adding a city is one JSON file, no code |

## Key technical concepts settled

**`NetworkArtifact`** — a build output, not a database record. Derived, immutable, versioned,
always reproducible from (zip bytes + city config). Holds the scene payload, a trip index
(`trip_id → shape_id`), and a manifest (version, source ETag, `feed_end_date`, build time).
Two read-only consumers: the server ships the payload; the realtime pipeline uses the index.

**`INetworkArtifactStore`** — where artifacts live. Disk today, blob storage later, no caller
changes. Also the seam if artifact building ever becomes a scheduled job.

**Versioning is load-bearing, not bookkeeping.** A `frame` references shape ids valid only in
one artifact version. Swapping mid-dwell makes every train vanish. Hence: swap only at a city
switch, `network` first, then frames.

**`shapeFraction`** — fraction along a shape polyline, one float per vehicle. The renderer
never sees a latitude. Shipping lat/lon instead would force every client to solve
nearest-point-on-polyline per vehicle per frame.

**Mercator units are not ground metres** — stretched by `1/cos(latitude)`. Boston's 22 km
radius is ~29.6 km of plane distance. Omitting the correction shrinks every extent by a
quarter and still looks plausible.

**Pipeline order matters:** clip *before* simplify, so Douglas–Peucker doesn't spend its
tolerance budget on geometry that runs 40 km off-screen.

## Conventions established (CLAUDE.md)

- **No references to Claude/AI/agents** anywhere: code, comments, commits, docs, file names,
  test names, log strings. No `Co-Authored-By` or "Generated with" trailers.
- **Version control:** the developer commits and pushes; Claude never runs `commit`, `push`,
  `merge`, `rebase`, `reset`, `tag`, or `add`. Read-only git is fine. Claude supplies a
  ready-to-paste commit message with each unit of work.
- **Naming:** readable words only. Prefix truncation OK (`intervalMs`, `maxLen`, `seq`);
  stubs banned (`t`, `pt`, `v`, `i`, `cfg`, `req`). `x`/`y` only as members of a point type.
- **Unit suffixes required:** `intervalMs`, `dwellMs`, `coreRadiusKm`, `toleranceM`, `lengthM`.

## Spec review findings, all fixed

Two self-review passes plus a manual review found and corrected:
`IGeometryArtifactStore` → `INetworkArtifactStore`; `network.frame` colliding with the
`frame` message type → renamed to `extent` across 14 sites; a units bug (`interval: 20`
documented as milliseconds) → `intervalMs`; a circular definition between §4 and §5; a wrong
cross-reference; `tz` → `timezone` (which had silently diverged from the config's spelling);
`"static"` → `"staticFeed"` (a C# keyword); vestigial `counts.scope` dropped; unused `dir`
field dropped; `*Sec` standardized to `*Ms`; an overstated "pure functions" claim corrected;
C#-type-to-wire-discriminator mapping added.

## Plan split

The spec's §14 build order became five plans, each producing working software on its own:

1. **Static geometry pipeline (.NET)** — written. `build-artifact mbta` emits a validated artifact
2. Static renderer (TS) — Boston's map on screen from that file
3. Realtime + SSE server — live dots, tweening
4. Chrome + rotation — bottom rail, multi-city crossfade
5. Hardening — backoff, `stale`, `/healthz`, refresh

Plans 2–5 get written as each lands, so they can absorb what the previous one taught.
