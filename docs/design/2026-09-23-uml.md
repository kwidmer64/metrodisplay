# MetroDisplay — UML Diagrams

Structural and behavioural models for the system described in
`docs/specs/2026-09-22-metrodisplay-design.md` and implemented by the plans under
`docs/plans/`.

Diagrams are Mermaid, so they render on GitHub and in any Markdown preview with Mermaid
support, and they diff as text.

**Implementation status:** `Contracts`, `Gtfs.Static` and `Tools` are fully specified by
Plan 1. `Realtime`, `Server` and `web/` are designed in the spec but not yet planned in
detail, so the diagrams covering them model intent rather than committed signatures.

## 1. Component and package structure

```mermaid
flowchart TB
  subgraph agency["«external» Transit agency"]
    staticZip["GTFS static archive<br/>routes, trips, shapes, stops"]
    vehiclePositions["GTFS-RT VehiclePositions"]
    serviceAlerts["GTFS-RT ServiceAlerts"]
  end

  subgraph ingest["Ingest"]
    gtfsStatic["«assembly» MetroDisplay.Gtfs.Static<br/>the only component that parses GTFS CSV"]
    realtime["«assembly» MetroDisplay.Realtime<br/>the only component that decodes protobuf"]
    artifactStore[("«interface» INetworkArtifactStore<br/>file system today, blob storage later")]
  end

  subgraph serve["Serve"]
    server["«assembly» MetroDisplay.Server<br/>rotation scheduler, SSE hub,<br/>artifact refresh, health endpoint"]
  end

  subgraph display["Display"]
    browser["«package» web/<br/>TypeScript, canvas2d"]
    kiosk["Raspberry Pi kiosk<br/>later"]
  end

  contracts["«assembly» MetroDisplay.Contracts<br/>scene DTOs, artifact records, city config<br/>zero dependencies"]
  tools["«assembly» MetroDisplay.Tools<br/>build-artifact CLI"]
  cityConfig["cities/*.json"]

  staticZip -->|"conditional GET, daily"| gtfsStatic
  vehiclePositions -->|"poll, 15-30s"| realtime
  serviceAlerts -->|"poll, 60s"| realtime
  cityConfig --> gtfsStatic

  gtfsStatic -->|"PutAsync"| artifactStore
  artifactStore -->|"GetLatestAsync"| server
  artifactStore -->|"GetAsync by version"| realtime
  realtime -->|"frame, alerts"| server
  server -->|"SSE"| browser
  server -.->|"SSE"| kiosk

  gtfsStatic -.->|"«uses»"| contracts
  realtime -.->|"«uses»"| contracts
  server -.->|"«uses»"| contracts
  tools -.->|"«uses»"| gtfsStatic
  browser -.->|"types generated from"| contracts
```

`Gtfs.Static` and `Realtime` never call each other. They meet only through a
`NetworkArtifact` referenced by version id — which is why a GTFS CSV concern can never leak
into the protobuf component, and vice versa.

### The same structure in n-layer terms

| Component | n-layer equivalent |
|---|---|
| `MetroDisplay.Contracts` | The shared model assembly. Every layer references it; it references nothing. |
| `MetroDisplay.Gtfs.Static`, `MetroDisplay.Realtime` | Business Layer — the transforms. Their feed clients are the inbound half of the Data Access Layer. |
| `INetworkArtifactStore` / `FileNetworkArtifactStore` | Data Access Layer — persistence, behind an interface. |
| `MetroDisplay.Server` | Presentation Layer — serves the wire contract over SSE. |
| `web/` | Presentation Layer — the view. |

The one mechanical difference from textbook n-layer: `INetworkArtifactStore` is declared next
to the business code that consumes it, not inside a separate data assembly that the business
code references. The compile-time dependency points inward; runtime flow is unchanged — the
business code still calls the store, exactly as it would in n-layer.

## 2. Class — wire contract DTOs

`MetroDisplay.Contracts`. These serialize directly to the `network` message in spec §8, and
the TypeScript renderer types are generated from them.

```mermaid
classDiagram
  direction TB

  class NetworkScene {
    <<record>>
    +string ArtifactVersion
    +CityInfo City
    +ExtentInfo Extent
    +IReadOnlyList~LineScene~ Lines
    +IReadOnlyList~StationScene~ Stations
    +IReadOnlyList~EdgeLabel~ EdgeLabels
  }

  class CityInfo {
    <<record>>
    +string Id
    +string Name
    +string Agency
    +string Timezone
  }

  class ExtentInfo {
    <<record>>
    +double Aspect
    +double CoreRadiusKm
    +double SpanKm
  }

  class LineScene {
    <<record>>
    +string Id
    +string Name
    +string Color
    +IReadOnlyList~ShapeScene~ Shapes
  }

  class ShapeScene {
    <<record>>
    +string Id
    +IReadOnlyList~double~ Points
    +double LengthM
  }

  class StationScene {
    <<record>>
    +double X
    +double Y
    +string Name
    +int Rank
  }

  class EdgeLabel {
    <<record>>
    +double X
    +double Y
    +string Text
    +double Angle
    +string Line
  }

  NetworkScene "1" *-- "1" CityInfo
  NetworkScene "1" *-- "1" ExtentInfo
  NetworkScene "1" *-- "0..*" LineScene
  NetworkScene "1" *-- "0..*" StationScene
  NetworkScene "1" *-- "0..*" EdgeLabel
  LineScene "1" *-- "1..*" ShapeScene
```

`ShapeScene.Points` is a flat `[x0, y0, x1, y1, ...]` array of normalized coordinates, not a
list of point objects. One array of doubles per shape instead of thousands of two-field
objects is the difference between a ~200 KB scene and a multi-megabyte one.

Nullable in the C#, shown without the marker above for diagram legibility:
`ArtifactManifest.FeedEndDate`, `CityConfig.RouteFilter`, `FeedSource.Headers`,
`RouteFilter.Include`, `RouteFilter.Exclude`.

`ExtentConfig.Core` is `[latitude, longitude]` and `CoreRadiusKm` is **ground** distance, not
Mercator plane distance. Converting between them is `MercatorProjector`'s job, and skipping
that conversion shrinks every extent by roughly a quarter at Boston's latitude while still
looking plausible.

## 4. Class — geometry value types and transforms

Every transform here is a static class over immutable value types: no state, no injection,
nothing to mock. That is what lets the pipeline tests run against a synthetic fixture with no
network and no API keys.

```mermaid
classDiagram
  direction TB

  class GeoPoint {
    <<readonly record struct>>
    +double Latitude
    +double Longitude
  }

  class PlanePoint {
    <<readonly record struct>>
    +double X
    +double Y
  }

  class ExtentRectangle {
    <<readonly record struct>>
    +double MinX
    +double MinY
    +double MaxX
    +double MaxY
  }

  class ClippedPolyline {
    <<record>>
    +IReadOnlyList~PlanePoint~ Points
    +bool ExitsAtStart
    +bool ExitsAtEnd
  }

  class MercatorProjector {
    <<static>>
    +Project(GeoPoint point) PlanePoint
    +GroundMetresToPlane(double groundMetres, double latitudeDegrees) double
    +PlaneMetresToGround(double planeMetres, double latitudeDegrees) double
  }

  class ExtentCalculator {
    <<static>>
    +Calculate(ExtentConfig config, IEnumerable~PlanePoint~ contentPoints) ExtentRectangle
  }

  class PolylineClipper {
    <<static>>
    +Clip(IReadOnlyList~PlanePoint~ points, ExtentRectangle extent) IReadOnlyList~ClippedPolyline~
  }

  class PolylineSimplifier {
    <<static>>
    +Simplify(IReadOnlyList~PlanePoint~ points, double toleranceInPlaneUnits) IReadOnlyList~PlanePoint~
  }

  class CoordinateNormalizer {
    <<static>>
    +Normalize(IReadOnlyList~PlanePoint~ points, ExtentRectangle extent) IReadOnlyList~double~
  }

  MercatorProjector ..> GeoPoint : consumes
  MercatorProjector ..> PlanePoint : produces
  ExtentCalculator ..> PlanePoint : consumes
  ExtentCalculator ..> ExtentRectangle : produces
  PolylineClipper ..> ExtentRectangle : consumes
  PolylineClipper ..> ClippedPolyline : produces
  PolylineSimplifier ..> PlanePoint : consumes
  CoordinateNormalizer ..> ExtentRectangle : consumes
```

The call order between these is fixed and not obvious: project, compute extent, **clip, then
simplify**. Simplifying first spends the Douglas–Peucker tolerance budget on geometry that
runs 40 km off-screen and is about to be discarded anyway.

`StaticFeedResult.Content` is `byte[]?` — null exactly when `NotModified` is true. `ETag` is
nullable for the same reason. The `Get*` methods on `INetworkArtifactStore` return null when
nothing matches; nullable markers are dropped above for diagram legibility.

Both interfaces exist for the same reason: they are the two places this system touches the
outside world. Everything between them is a pure function over bytes.

## 6. Sequence — building an artifact

`dotnet run --project src/MetroDisplay.Tools -- build-artifact mbta`

```mermaid
sequenceDiagram
  autonumber
  actor developer as Developer
  participant cli as Tools.Program
  participant loader as CityConfigLoader
  participant feed as HttpStaticFeedClient
  participant store as FileNetworkArtifactStore
  participant reader as GtfsArchiveReader
  participant builder as NetworkArtifactBuilder
  participant geometry as Geometry stages
  participant validator as ArtifactValidator

  developer->>cli: build-artifact mbta
  cli->>loader: Load(cities/mbta.json)
  loader-->>cli: CityConfig, env vars interpolated

  cli->>store: GetLatestAsync(mbta)
  store-->>cli: previous artifact or null
  cli->>feed: FetchAsync(staticFeed, knownETag)

  alt 304 Not Modified
    feed-->>cli: StaticFeedResult, NotModified
    cli-->>developer: Feed unchanged. No work done.
  else 200 OK
    feed-->>cli: StaticFeedResult with content and new ETag
    cli->>reader: Read(archiveStream)
    note right of reader: routes, trips, shapes, stops, feed_info only.<br/>stop_times.txt is never opened. It is most of<br/>the zip and none of it matters here.
    reader-->>cli: GtfsArchive

    cli->>builder: Build(config, archive, newETag)
    builder->>builder: RailRouteSelector.Select, route_type filter
    builder->>builder: ShapeDeduplicator.Deduplicate, collapse identical geometry

    alt no rail shapes survive
      builder-->>cli: throw ArtifactValidationException
      cli-->>developer: rejected. Previous artifact retained.
    end

    builder->>geometry: MercatorProjector.Project, every shape point
    geometry-->>builder: plane points
    builder->>geometry: ExtentCalculator.Calculate(core, coreRadiusKm)
    geometry-->>builder: ExtentRectangle

    loop each surviving shape
      builder->>geometry: Clip, then Simplify, then Normalize
      geometry-->>builder: normalized points and exit flags
    end

    builder->>builder: TripIndexBuilder.Build
    builder->>validator: Validate(artifact)
    validator-->>builder: ok
    builder-->>cli: NetworkArtifact

    cli->>store: PutAsync(artifact)
    store-->>cli: mbta@2026-09-01.a3f1
    cli-->>developer: wrote .artifacts/mbta/mbta_2026-09-01.a3f1.json
  end
```

Validation happens **before** `PutAsync`, never after. An agency publishing a broken feed
overnight must not be able to blank the display.

## 7. Sequence — display connect and one rotation cycle

Models spec §8 flow rules and §9 rotation. Implemented in Plans 3 and 4.

```mermaid
sequenceDiagram
  autonumber
  participant display as Display, web/
  participant server as Server SSE hub
  participant rotation as Rotation scheduler
  participant store as INetworkArtifactStore
  participant realtime as Realtime poller

  display->>server: GET /stream, EventSource
  server-->>display: hello, protocol and serverTime
  server-->>display: network, artifactVersion and city and extent and lines
  server-->>display: latest frame, then current alerts
  note over display: A display that reboots is correct within one<br/>round trip, not within one poll interval.

  loop every ~20s for the whole dwell
    realtime->>realtime: poll VehiclePositions, decode, join to shapes
    realtime->>server: frame, seq and vehicles and counts
    server-->>display: frame
    display->>display: tween each vehicle along its shape polyline
  end

  rotation->>store: at dwell minus 30s, GetLatestAsync(nextCityId)
  store-->>rotation: NetworkArtifact for the next city
  rotation->>realtime: start poller for the next city
  note over rotation,realtime: Prefetching is what makes the switch land on a<br/>populated map instead of an empty one that<br/>fills in over the next 20 seconds.

  rotation->>server: dwell elapsed, switch
  activate server
  server->>server: hold frames referencing the outgoing artifact
  server-->>display: network, next city
  server->>server: resume frame flow
  deactivate server
  note over server,display: Ordering interlock. A frame referencing shape ids<br/>from artifact N must never precede the network for N,<br/>or every train on screen silently vanishes.
  display->>display: crossfade ~700ms to the new scene
```

## 8. State — artifact lifecycle

Why versioning is load-bearing rather than bookkeeping.

```mermaid
stateDiagram-v2
  [*] --> Absent : city added to registry

  Absent --> Building : boot, or a daily refresh returns 200
  Building --> Validating : pipeline completed
  Building --> Absent : fetch failed and nothing cached

  Validating --> Current : rail shapes present
  Validating --> Rejected : zero rail shapes

  Rejected --> Current : previous artifact retained
  note right of Rejected
    A broken agency publish cannot blank the display.
    The old artifact keeps serving until a valid
    replacement arrives.
  end note

  Current --> Refreshing : daily conditional GET
  Refreshing --> Current : 304 Not Modified
  Refreshing --> Building : 200 OK, new content

  Current --> PendingSwap : a newer version built while this one is on screen
  PendingSwap --> Superseded : next switch to this city
  note right of PendingSwap
    Swapping mid-dwell would leave frames referencing
    shape ids the displayed network has never seen.
    The swap waits for a city switch. Network first,
    then frames.
  end note

  Superseded --> [*] : retained on disk, no longer served
```

## 9. State — per-city feed health

Models the detection and response columns of spec §12.

```mermaid
stateDiagram-v2
  [*] --> Live

  Live --> Backoff : realtime poll returns 5xx or times out
  Backoff --> Live : a poll succeeds
  Backoff --> Backoff : retry, exponential, capped at 5 min

  Live --> Stale : 3 consecutive missed intervals
  Stale --> Live : a frame arrives
  note right of Stale
    The map keeps drawing, flagged stale.
    A frozen map reads as feed down. An empty one
    reads as app broken. At 2 a.m. a genuinely empty
    system must not look like a dead feed.
  end note

  Live --> Degraded : unmatched trip rate above 30 percent
  Degraded --> Live : rate recovers
  note left of Degraded
    Unmatched trip rate measures whether the static
    to realtime join still works, which is the thing
    that actually matters. feed_end_date is an agency
    field they may not maintain.
  end note

  Live --> Dropped : no artifact and static fetch failed at boot
  Dropped --> Live : a later refresh produces a valid artifact
```

## 10. Activity — projecting a vehicle onto its shape

Runs once per vehicle per poll in `MetroDisplay.Realtime`.

```mermaid
flowchart TD
  entity([VehiclePosition entity decoded]) --> hasPosition{"position present?"}
  hasPosition -->|no| dropSilent[/"drop silently, normal and common"/]
  hasPosition -->|yes| tripLookup{"trip_id resolves in<br/>TripIndex.ShapeIdByTripId?"}

  tripLookup -->|yes| haveShape[shape id resolved]
  tripLookup -->|no| routeLookup{"route_id resolves to<br/>the route's primary shape?"}
  routeLookup -->|yes| haveShape
  routeLookup -->|no| dropCounted[/"drop and count. Above 30% marks the city degraded"/]

  haveShape --> nearest["nearest point on THAT shape only"]
  nearest --> constraint["never a global nearest-point search"]
  constraint --> fraction["emit shapeFraction, one float"]

  fraction --> identity{"vehicle.id present<br/>and stable?"}
  identity -->|yes| useVehicleId["identifier = vehicle.id"]
  identity -->|no| useTripId["identifier = trip_id"]

  useVehicleId --> emit([into the frame message])
  useTripId --> emit
```

Constraining the nearest-point search to the vehicle's own shape is not an optimisation, it
is correctness. A global search puts trains on the wrong line wherever routes share
trackage, which is most of the MBTA Green Line core and all of BART's Market Street tunnel.

Emitting `shapeFraction` rather than latitude and longitude is what keeps every client cheap.
Shipping coordinates would force each display to solve nearest-point-on-polyline, an
O(segments) search per vehicle per frame, before it could draw a single dot.

## 11. Open discrepancies

Found while drawing these. Neither is urgent; both want a decision before the code sets.

1. **Where the CLI lives.** Spec §3 lists `MetroDisplay.Gtfs.Static` as "Library + CLI".
   Plan 1's file structure puts the CLI in a separate `src/MetroDisplay.Tools/Program.cs`.
   The plan's split is the better shape — it keeps a host entry point and its argument
   parsing out of a library that `Server` and `Realtime` both reference — so spec §3's
   project list should be updated to match, rather than the other way round.

2. **Where `INetworkArtifactStore` is declared.** Plan 1 puts both the interface and
   `FileNetworkArtifactStore` under `MetroDisplay.Gtfs.Static/Storage/`. `Server` and
   `Realtime` are both consumers of the store, so each would have to reference
   `Gtfs.Static` — the component that parses CSV — purely to see a persistence interface.
   Moving the interface into `MetroDisplay.Contracts` and leaving the file implementation in
   `Gtfs.Static` costs nothing now and avoids that reference later.
