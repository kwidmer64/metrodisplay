How should the network geometry be drawn?

Same fake 3-line system, three renderings. Dim lines = track, bright dots = live vehicles. This is the single biggest look-and-feel decision, and it drives how much per-city hand-work each new city needs.

A — True geographic

Raw shapes.txt polylines, projected and fit to the viewport. The map is the city's real shape.

New city cost: zero — drop in a feed config, it just works.
Risk: dense downtowns turn into an unreadable knot; a long suburban branch squashes the core into 10% of the screen.

B — Simplified geographic recommended

Same true bearings, but polylines run through Douglas–Peucker to strip GPS noise, plus a tuned line weight and minimum station spacing.

New city cost: zero — one tolerance number, auto-derived from system extent.
Why: keeps geographic honesty (recognisable city shape) and the wireframe crispness, and it's the only option where vehicle lat/lon maps to the screen with no lookup table.

C — Octolinear schematic

Beck-style diagram: every segment snapped to 0°/45°/90°, spacing evened out. What a real transit map looks like.

New city cost: high — good octolinear layout is an NP-hard optimisation; in practice it's hand-drawn per city.
Risk: a vehicle's lat/lon no longer has a screen position — you must snap it to the nearest track segment and interpolate. Breaks the "any city is a config file" goal.

Worth knowing: B and C aren't exclusive forever. If the scene contract carries projected coordinates rather than lat/lon, a per-city hand-drawn schematic can be added later as an optional override for the 2–3 cities you care most about, without touching the pipeline.
